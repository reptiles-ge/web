# Species editor: audit and Super Analysis

Audit date: 2026-10-09. Local development feature, not a public AI endpoint.

## What existed

The four independent controls remain available in `SpeciesPageAnalysis.tsx`, along with records import and the configurable workflow. Their entry points are the local-only `species-analysis`, `species-texts`, and `species-workflow` API routes. They require a local admin server, a localhost request and matching origin. UI copy lives in `messages/{ka,en,ru,tr}.json` under `pageAnalysis`.

The prior configurable shared-branch workflow committed each stage sequentially, but passed no structured findings/evidence to the next step. Its default order put texts second. It could publish completed commits after a later failure. Separate text and analysis locks did not coordinate. Same-branch UI showed no live stage transitions until the response finished. These legacy behaviors are preserved for the existing workflow except for a shared species lock; Super Analysis has stricter semantics.

`runCodexProcess` provides subprocess timeout/error propagation. It explicitly selects `gpt-6-sol` for local editor calls, with Extra High (`xhigh`) reasoning for research, Super Analysis and text processing. The inherited desktop default `gpt-6.1-sol` was rejected by the signed-in CLI with HTTP 400. Global Codex configuration is preserved. Standalone research uses the original prompts and publishing behavior. Standalone text rewriting still uses its existing schema and link/selection validation. No Telegram notification behavior of those routes was removed. Super Analysis uses the existing admin Telegram notifier once the background job completes or fails, including thrown errors and interruptions detected after a server restart. Success includes the PR URL (or a no-change result); failure includes the stage, completed count and a bounded error message. Notification failures do not change the analysis outcome.

## Chosen execution model

One master editorial contract (`src/prompts/species-super-analysis.md`) with stage-specific responsibilities; four separate **read-only** Codex calls. No concatenation of four old prompts, and no new agent framework.

1. **Analysis:** current-page/source audit; evidence-backed factual corrections and additions; unresolved issues retained as findings.
2. **Lookalikes:** catalog screening and current direct/reverse review, evidence-backed pair decisions and matching comparison prose.
3. **Links:** use the updated content and approved pair decisions; only link syntax changes, identical visible prose.
4. **Texts:** page-wide editorial pass, using all three validated results. No new facts/sources; preserve destinations, numbers, scientific names and scope.

Each output is strict JSON validated with Zod. `--output-schema` supplies the same contract to Codex. Prior evidence/findings/decisions are passed forward; prior before/after bodies are omitted because the next snapshot already contains applied changes. The catalog supplies compact identities and source paths instead of copying every other species' prose into every call. Research is enabled for the first two stages; the final stages use the supplied facts. Each call has a 45-minute upper bound and fails closed.

A proposed edit includes explicit before/after text in KA/EN/RU/TR, a field path, reason and evidence IDs. Source records require URL, exact claim, taxon/scope, locator and excerpt. Factual edits require verified evidence attached to a profile reference. Unsupported, unresolved or contradicted evidence cannot authorize a scientific edit. Shared/derived/identity fields cannot be patched. Original values must match the current snapshot, and all locale outputs are prepared/validated before any file is written. YAML round-trip and frontmatter structural validation preserve the MDX body and unrelated keys; KA modification date is updated programmatically.

Link-stage validation checks renderable field paths, unchanged visible text, known non-self destinations and locale target parity. Final text validation protects inline link targets, numeric values, catalog scientific names, compact IUCN codes and Giurza's reproduction paragraph structure. Lookalike registry updates are parsed with TypeScript's AST, with additions confined to the target and removals applied in both directions. Every existing pair must receive an explicit decision; uncertain pairs are retained for review.

The existing worktree/publishing mechanism is reused. Super Analysis enforces the fixed order server-side, checks local content against the remote base, rejects a conflicting open species PR, and publishes **only after all four stages pass internal content validation**. Compilation, typecheck, lint, tests and build are left to the owner; the workflow does not run project-check commands. The single result is a draft PR with the `content` label and stage reports. No-op runs return reports without creating a PR. Failure discards intermediate changes instead of publishing a partial PR. Existing standalone/custom workflows retain their separate behavior.

## Progress, reruns and failures

`species-super-analysis/route.local.ts` starts a background job and returns immediately. Same-origin GET polling provides current stage and completed reports. `SpeciesSuperAnalysis` shows four ordered stages, findings and a single PR link. Closing the panel or reloading the page does not restart server work. Concurrent submissions return the same active job, request IDs deduplicate replays, and a shared process-level species lock coordinates Super Analysis with standalone analysis/text processing. No long-lived HTTP response needs to survive the AI calls.

Latest job snapshots are saved atomically below the OS temporary directory, namespaced by repository path. A new local server process recognizes a persisted running job as interrupted. It does not claim it can resume an AI call or reuse stale validation. Restart with a fresh context after reviewing any existing PR. Timeout/model/schema/evidence/stale-input/check failures are surfaced with completed reports retained. Network polling retries without launching a second analysis. Git push failures preserve the local branch using the existing recovery mechanism.

Missing, unknown or unverified evidence on a proposed edit/source/pair triggers one read-only repair call with the precise owner and evidence statuses. The rejected response remains available to that call; nothing is applied before successful validation. The model must inspect support or withdraw the proposal into review findings, never relabel unsupported evidence merely to pass. A second evidence failure stops the stage. Other validation failures are not retried. Tests cover successful repair, the retry limit and preservation of all locale files on failure.

## Verification boundaries

Program validation checks structure, ownership, references, deterministic invariants. It cannot prove that a model correctly understood a paper, that every semantic qualification survived, or that an excerpt/URL is authentic. `verified` is an AI source-inspection assessment, **not human approval or a factual guarantee**. The final artifact is deliberately a draft for editorial review. Unsupported changes must remain findings. No automatic merge or deployment occurs.

Automated tests cover the real inventory (including description/FAQ questions/stats/risk templates/occurrence summaries), strict field/evidence/locale gates, YAML preservation, bidirectional pairs, ordered fresh-context handoffs, fail-stop behavior, API origin protection, duplicate jobs, reconnecting UI, and withholding push/PR after stage failures and skipping project-check commands. AI/GitHub are mocked in execution tests; production model output quality, live web research and real GitHub publishing still require a supervised acceptance run. Development verification does not launch a paid four-stage research run or publish a content PR.

## Coloration

`identification.coloration` is optional four-locale source-backed prose about colour, markings and scoped variation. `identification.colors` is an optional array of fixed palette codes from `speciesColors.ts`; labels are shared localized UI, swatches illustrative. Compilation normalizes optional identification summary/traits without changing legacy data. Both generic and Giurza identification render the new block only when content exists; Giurza retains its existing UI palette as fallback.

The factual stage explicitly researches coloration and can add prose/palette entries with verified evidence and profile references. Palette edits are confined to that stage and must match across locales; unsupported RGB strings/codes are rejected. Links and final text editing include coloration prose, while palette codes are protected from rewriting. Standalone factual analysis and text processing also cover coloration. Regression test cases were added; project checks remain the owner's responsibility.
